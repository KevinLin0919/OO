1專案概覽

背景與目標

本次期末作業要求在保留所有現有功能的前提下，將一個已實作的 Java Swing UML 編輯器（OopsUMLEditor）重構為符合物件導向設計原則的架構。 重構不新增任何功能，而是透過引入設計模式，讓程式碼結構更清晰、可讀性更高、 更符合 OCP（開放封閉原則）與 DIP（依賴反轉原則）。

核心挑戰在於：如何在不破壞既有行為的前提下，識別「壞味道」 (bad smells)，並以正確的設計模式系統性地消除它們。

🎯
MVC 分層

抽出 UMLModel，Canvas 只負責繪製，業務邏輯完全歸 Model

🏭
Factory Method

ShapeFactory / LinkFactory 消除 CreateObjectMode 與 CreateLinkMode 的 if-else / switch

👁️
Observer Pattern

ModelObserver 介面，UMLModel 通知 Canvas 重繪，解除雙向耦合

📐
六種模式標示

Strategy、Composite、Template Method、Factory Method、Observer、MVC 全在程式碼與 Class Diagram 中明確標示

重構前後架構對比

面向 重構前（壞味道） 重構後（設計模式）
物件建立 if (isRect) new RectObject(...) else new OvalObject(...) ShapeFactory.create(x, y, w, h)（Factory Method）
連線建立 switch(linkType) { case ASSOCIATION: ... } LinkFactory.create(src, srcPort, dst, dstPort)（Factory Method）
畫面更新 Canvas 持有所有資料，直接呼叫 repaint() UMLModel 呼叫 notifyObservers()，Canvas 實作 ModelObserver（Observer）
業務邏輯位置 散布在 Canvas 的大量方法中（groupSelectedObjects、getObjectAt 等） 集中於 UMLModel；Canvas 只剩繪製與事件轉發（MVC）
Canvas 依賴 持有 List<UMLObject>、List<ConnectionLine> 只持有 UMLModel model 一個參照

本次專案使用 Claude Code（Anthropic 官方 CLI 工具）作為主要 AI 協作工具。 Claude Code 運行在終端機中，可以直接讀取、撰寫、修改專案中的所有原始碼檔案， 並執行 Shell 命令（如 build.bat）來驗證編譯結果。

3與 AI 的溝通流程

整體溝通策略

與 AI 的溝通並非一次性的「給需求 → 收程式碼」，而是採用漸進式、有確認點的對話流程。 核心原則是：先讓 AI 理解問題的本質與約束，再讓它提出設計方案，人類確認後才進入實作。

Phase 0 — 背景建立
提供課程背景與評分標準
告知 AI 這是 OOAD 期末作業，說明評分標準（功能完整度、OO 設計品質、 程式碼可讀性、程式碼與設計圖對應、對專案的熟悉度）， 讓 AI 了解設計決策的優先順序。
Phase 1 — 確認工具
詢問是否可以用 Speckit 的斜線命令
確認 Claude Code CLI 環境中已有 /speckit.* 命令可用， 詢問應該給哪個 prompt 作為 /speckit.specify 的輸入。
Phase 2 — 需求規格化
/speckit.specify — 自然語言 → 結構化規格
提供包含六大設計目標的完整描述 prompt，Speckit 自動生成含 5 個 User Story、功能需求、成功標準的 spec.md。
Phase 3 — 架構設計
/speckit.plan — 規格 → 技術架構
無需額外 prompt（/speckit.plan 直接讀取 spec.md）， AI 自動研究並輸出包含完整檔案結構、介面契約、技術決策的 plan.md。
Phase 4 — 任務拆解
/speckit.tasks — 架構 → 可執行任務清單
同樣無需額外 prompt，AI 讀取 plan.md 輸出 18 個任務（T001–T018）， 標示依賴關係、可平行執行的任務（[P] 標記），以及每個任務的精確檔案路徑。
Phase 5 — 逐步實作
/speckit.implement — 任務清單 → 實際程式碼
AI 依序讀取現有程式碼、撰寫/修改檔案、執行 build.bat 驗證， 並即時修復因架構變動（如 Canvas 建構子變更）產生的依賴問題。

5架構設計：/speckit.plan

AI 的設計決策過程

/speckit.plan 的核心工作是：在讀取 spec.md 後，先研究技術問題（research.md）， 再輸出完整的系統架構（plan.md + contracts/）。 以下是 AI 在 plan 階段做出的關鍵設計決策：

決策 1：UMLModel 是否需要 refresh() 方法？

問題：在 SelectMode 的拖曳操作（MOVE、RESIZE）中，物件的位置與大小是透過 obj.move(dx, dy) 與 obj.setBounds(...) 直接修改， 這些呼叫不經過 UMLModel 的 mutating 方法，因此不會觸發 notifyObservers()。

解法：在 UMLModel 中新增 public void refresh() 方法， 它僅呼叫 notifyObservers() 而不修改任何狀態。 SelectMode 在拖曳期間呼叫 model.refresh() 觸發重繪， 避免在 Mode 層中直接呼叫 canvas.repaint()（會破壞 MVC 分層）。 

// UMLModel.java — 拖曳操作的重繪觸發點
public void refresh() {
    notifyObservers(); // 不修改狀態，只觸發 View 重繪
}

決策 2：ShapeFactory 要不要包含 drawPreview()？

問題：CreateObjectMode.draw() 在拖曳時需要繪製預覽外框 （Rect 畫矩形、Oval 畫橢圓）。若保留 instanceof 判斷， 違反 OCP 原則，也讓 Mode 層反向依賴具體類型。

解法：在 ShapeFactory 介面中新增 void drawPreview(Graphics2D g, int x, int y, int w, int h)， 由各具體 Factory 實作對應的預覽繪製邏輯。 

// ShapeFactory.java — 介面同時負責建立與預覽
public interface ShapeFactory {
    UMLObject create(int x, int y, int w, int h);
    void drawPreview(Graphics2D g, int x, int y, int w, int h);
}

決策 3：Canvas import Mode 的方式

問題：Canvas 持有 Mode currentMode 欄位， 但 Mode 介面在 oops.mode package， 而 Canvas 在 oops package——容易遺漏 import。

解法：明確加入 import oops.mode.Mode;（非 wildcard）， 避免因為 import oops.model.* 的 wildcard 範圍不包含 mode package 而產生的 cannot find symbol 編譯錯誤。

⚠️
這個問題在實際編譯時才被發現（AI 初稿遺漏了此 import）， 是一個很好的例子：「先讓 AI 產出草稿，再用編譯驗證」的重要性， 勝過「相信 AI 輸出永遠正確」。

關鍵實作步驟詳解

建立 UMLModel：將 Canvas 的業務邏輯全部遷移

Canvas 原本持有 List<UMLObject> objects、 List<ConnectionLine> lines、UMLObject hoveredObject， 以及超過 10 個業務方法。AI 在讀取 Canvas.java 全文後， 完整識別哪些方法屬於「業務邏輯」（應移至 UMLModel）， 哪些屬於「View 責任」（應留在 Canvas）。 

// UMLModel.java — 業務邏輯集中管理（節錄）
public class UMLModel {
    private final List<UMLObject> objects = new ArrayList<>();
    private final List<ConnectionLine> lines = new ArrayList<>();
    private final List<ModelObserver> observers = new ArrayList<>();

    public void addObject(UMLObject obj) {
        objects.add(obj);
        notifyObservers(); // 每個 mutating 方法都通知 Observer
    }

    private void notifyObservers() {
        for (ModelObserver o : observers) o.onModelChanged();
    }
}
重寫 Canvas 為純 View

Canvas 新增 private final UMLModel model 欄位， 建構子改為 Canvas(UMLModel model)， 並在建構子中呼叫 model.addObserver(this) 完成 Observer 訂閱。 paintComponent 直接讀取 model.getObjects() 與 model.getLines() 繪製。 

// MVC - View / Observer Pattern
public class Canvas extends JPanel
    implements MouseListener, MouseMotionListener, ModelObserver {

    private final UMLModel model;

    public Canvas(UMLModel model) {
        this.model = model;
        model.addObserver(this); // Observer Pattern：Canvas 訂閱 UMLModel
    }

    public void onModelChanged() { repaint(); } // Observer 收到通知後重繪
    public UMLModel getModel()   { return model; }
}
Factory Pattern：替換 CreateObjectMode 的 isRect 判斷

原本 CreateObjectMode 持有 boolean isRect， 在 mouseReleased 中有 isRect ? new RectObject(...) : new OvalObject(...)。 重構後改為注入 ShapeFactory factory，建立物件時只呼叫 factory.create(x, y, w, h)。 

// 重構前（壞味道）
UMLObject obj = isRect
    ? new RectObject(x, y, w, h)
    : new OvalObject(x, y, w, h);

// 重構後（Factory Method Pattern）
UMLObject obj = factory.create(x, y, w, h); // 不知道也不需要知道具體類型
Factory Pattern：替換 CreateLinkMode 的 switch

原本 CreateLinkMode 有一個 LinkType enum 和一個 createLine() 方法， 裡面是三分支的 switch。重構後整個 enum 和 switch 被刪除， 改由注入的 LinkFactory factory 負責建立連線。 

// 重構前（switch 壞味道）
switch (linkType) {
    case ASSOCIATION:    return new AssociationLine(src, srcPort, dst, dstPort);
    case GENERALIZATION: return new GeneralizationLine(src, srcPort, dst, dstPort);
    case COMPOSITION:    return new CompositionLine(src, srcPort, dst, dstPort);
}

// 重構後（Factory Method Pattern）
ConnectionLine line = factory.create(sourceObject, sourcePort, destPort.getOwner(), destPort);
canvas.getModel().addConnectionLine(line);
ToolPanel：依賴注入 (DI) 具體 Factory

ToolPanel 是整個依賴注入的「組裝點（Composition Root）」—— 在這裡決定每個按鈕要綁定哪個具體 Factory， 然後透過建構子注入傳遞給 Mode。 

// ToolPanel.java — 依賴注入的組裝點
JButton assocBtn = createModeButton("Association", "association",
    () -> new CreateLinkMode(new AssociationLinkFactory()));

JButton rectBtn = createObjectButton("Rect", "rect",
    new RectShapeFactory());  // 注入具體 Factory

7六種設計模式在本專案中的應用

MVC Model-View-Controller 架構

問題：Canvas 原本同時負責顯示資料、管理資料、處理業務邏輯，職責混雜。

解法：

  • Model（UMLModel）：持有所有資料，提供業務邏輯 API
  • View（Canvas）：只讀取 Model 資料繪圖，實作 ModelObserver
  • Controller（UMLEditor + ToolPanel）：處理使用者輸入，協調 Model 和 View

好處：UMLModel 可以獨立進行單元測試；UI 可以替換而不影響 Model。

Observer Observer Pattern

問題：UMLModel 需要讓 Canvas 知道狀態改變，但不能直接持有 Canvas 參照（會破壞 MVC 分層）。

解法：

// Subject（UMLModel）持有觀察者清單
private final List<ModelObserver> observers = new ArrayList<>();
public void addObserver(ModelObserver o) { observers.add(o); }
private void notifyObservers() { for (ModelObserver o : observers) o.onModelChanged(); }

// Observer（Canvas）實作介面
public class Canvas implements ModelObserver {
    public void onModelChanged() { repaint(); }
}

好處：UMLModel 不需要知道 Canvas 的存在，僅依賴 ModelObserver 介面。

Strategy Strategy Pattern（既有，強化標示）

應用位置：Mode 介面 + SelectMode、CreateObjectMode、CreateLinkMode

Canvas 持有一個 Mode currentMode 參照，所有滑鼠事件都委派給 currentMode 處理。 切換工具按鈕時，只需替換 currentMode 的實例，不需要修改 Canvas 的任何程式碼。 

// Canvas 不知道 Mode 的具體類型，只透過介面呼叫
public void mousePressed(MouseEvent e) {
    if (currentMode != null) currentMode.mousePressed(e, this);
}

Factory Method Factory Method Pattern（新增）

應用位置：oops.factory package — ShapeFactory + LinkFactory + 5 個具體工廠

每個按鈕（Rect、Oval、Association、Generalization、Composition）在建立時， ToolPanel 注入對應的具體 Factory。Mode 只透過 Factory 介面建立物件， 完全不知道具體類型，滿足 OCP（不需修改現有 Mode 類別就能新增形狀類型）。 

// 介面定義——Factory Method Pattern
public interface ShapeFactory {
    UMLObject create(int x, int y, int w, int h);
    void drawPreview(Graphics2D g, int x, int y, int w, int h);
}

// 具體工廠——Factory Method Pattern (Concrete Factory)
public class RectShapeFactory implements ShapeFactory {
    public UMLObject create(int x, int y, int w, int h) {
        return new RectObject(x, y, w, h);
    }
    public void drawPreview(Graphics2D g, int x, int y, int w, int h) {
        g.drawRect(x, y, w, h);
    }
}

Composite Composite Pattern（既有，標示強化）

應用位置：UMLObject（Component）、RectObject/OvalObject（Leaf）、CompositeObject（Composite）

Group 操作將多個物件包裝成一個 CompositeObject， Move 時遞迴移動所有子物件，從外部看起來與單一物件完全相同。 CompositeObject 可以再包含其他 CompositeObject（巢狀群組）。

Template Method Template Method Pattern（既有，標示強化）

應用位置（兩處）：

  • ConnectionLine.draw() = Template Method（骨架：畫線 → 呼叫 drawArrowHead）； drawArrowHead() = abstract hook（由 AssociationLine、GeneralizationLine、CompositionLine 各自實作）
  • UMLObject 的 draw()、contains()、initPorts() 均為 abstract hooks， 由 RectObject 和 OvalObject 各自實作

8遇到的挑戰與解決方式

挑戰 1：拖曳操作的重繪問題（AI 初稿 Bug）

問題描述：SelectMode 的 MOVE 和 RESIZE 動作中， 物件是透過 obj.move(dx, dy) 和 setBounds() 直接修改屬性， 不經過 UMLModel 的任何 mutating 方法，因此不會觸發 notifyObservers()， 畫面不會更新。

AI 初稿的錯誤：AI 第一次的 SelectMode 草稿呼叫了 model.notifyObserversDirectly()，但這個方法根本不存在。

解決方式：在與 AI 的對話中說明問題，AI 提出在 UMLModel 新增 public void refresh() 方法（僅呼叫 notifyObservers() 不修改狀態）， 並同步更新 SelectMode 使用 model.refresh()。

💬 對話紀錄（問題發現）

編譯後執行，發現拖曳時畫面不更新。追查後發現 SelectMode 呼叫了不存在的 model.notifyObserversDirectly()。討論後決定新增 UMLModel.refresh() 作為「手動觸發重繪」的公開 API， 而非讓 Mode 直接呼叫 canvas.repaint()（後者會破壞 MVC 分層）。

挑戰 2：Canvas 遺漏 Mode import

問題描述：Canvas.java 改寫後，import oops.model.* 的 wildcard 只涵蓋 oops.model package，而 Mode 介面在 oops.mode， 導致 private Mode currentMode 欄位的 Mode 無法解析。

解決方式：執行 build.bat 後，看到 error: cannot find symbol — class Mode， 立即在 Canvas.java 加入 import oops.mode.Mode;。

⚠️
教訓：AI 產出的程式碼即使邏輯正確，也可能有細節疏漏（如 import）。 「讓 AI 產出初稿 → 立即執行編譯驗證 → 修復問題」的循環 比「讓 AI 產出完美程式碼」更可靠、更高效。

挑戰 3：javac 在 WSL 環境中找不到

問題描述：本機環境為 Windows + WSL2， javac 安裝在 Windows 端，WSL bash 的 PATH 找不到。 AI 試圖在 WSL 直接執行 javac 失敗。

解決方式：改透過 /mnt/c/Windows/System32/cmd.exe /c "cd /d D:\OO\UML && build.bat" 呼叫 Windows 的 cmd.exe 執行 build.bat，成功取得編譯結果。

挑戰 4：ShapeFactory 的 drawPreview OCP 問題

問題描述：CreateObjectMode.draw() 需要在拖曳時預覽形狀。 AI 的初稿使用了 if (factory instanceof RectShapeFactory)， 這違反 OCP——若未來新增 TriangleShapeFactory，需要修改 CreateObjectMode 的程式碼。

解決方式：AI 自我發現了這個問題（「instanceof 是 OCP 違規」）， 主動在 ShapeFactory 介面新增 drawPreview()， 由各具體工廠實作對應的預覽繪製邏輯，Mode 只呼叫 factory.drawPreview(g, x, y, w, h)。

10心得反思：與 AI 協作的觀察

AI 協作效益最大化的三個關鍵

「先說清楚要什麼」比「直接問怎麼做」更有效

直接問 AI「幫我實作 Factory Pattern」容易得到不符合實際需求的答案。 透過 /speckit.specify 先把問題轉化為結構化的 User Story 與驗收條件， AI 在後續實作時才能做出符合需求的設計決策（例如 ShapeFactory 要包含 drawPreview， 因為「需求」中明確要求不能有 instanceof 判斷）。

「讓 AI 先提設計，人來審查」優於「讓 AI 直接寫程式碼」

在 /speckit.plan 階段，AI 提出了 refresh() 方法的設計方案， 解釋了為什麼拖曳操作需要它、以及為什麼不能直接呼叫 canvas.repaint()。 這個設計決策通過人工確認後才進入實作，比「讓 AI 直接寫然後才發現架構問題」 省下了大量的除錯時間。

「編譯驗證」是最可靠的 AI 輸出品質保證

AI 產生的程式碼在邏輯層面通常是正確的，但在細節層面（如 import、方法名稱拼寫） 可能有小疏漏。透過立即執行 build.bat 取得編譯器回饋， 遠比閱讀程式碼審查更快、更可靠。 這個流程也可以早期發現架構問題（如初稿呼叫不存在的 notifyObserversDirectly()）， 在問題擴散之前修正。

AI 目前的局限性

局限性 本次遇到的具體例子 因應方式
細節疏漏 Canvas 遺漏 import oops.mode.Mode; 每次修改後立即執行編譯驗證
第一稿可能有 Bug 呼叫不存在的 model.notifyObserversDirectly() 將設計討論放在實作之前（plan 先於 implement）
環境感知有限 不知道 WSL 找不到 javac 明確告知環境限制（WSL2 + Windows javac）
初稿設計不夠 OCP instanceof 判斷替代多型 提醒 AI OCP 原則，AI 可以自行修正

這個流程的可遷移性

Speckit 的 specify → plan → tasks → implement 四階段流程 並不局限於本次作業。這套流程本質上是「需求工程（Requirements Engineering）→ 系統設計（Architecture Design）→ 任務分解（Work Breakdown）→ 實作（Implementation）」的 AI 輔助版本， 對任何規模的軟體開發都適用。

核心觀念是：AI 是加速器，不是替代品。 AI 加速了文件撰寫、樣板程式碼生成、重複性修改， 但架構決策的理解、設計方案的審查、最終程式碼的掌握， 仍然需要開發者自身的判斷。

🎯
最重要的收穫 透過 AI 協作完成這次重構，最大的收穫不是節省了時間， 而是 AI 在每個設計決策時都能清楚說明「為什麼這樣設計」 （例如：為什麼 refresh() 要是 public 而不是讓 Mode 直接呼叫 repaint()？ 為什麼 ShapeFactory 要有 drawPreview() 而不是用 instanceof？）， 幫助建立起對設計模式的深層理解，而不只是「照範本套用」。
